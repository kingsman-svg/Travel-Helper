# 第二天：行程管理、Prompt 与 Advisor

实际完成日期：2026-10-22（Asia/Shanghai），按用户要求提前完成原排期第二天内容。

## 已完成的体验

填写出发地、目的地、起止日期、人数、全体总预算、预算包含项与偏好，生成结构化每日行程；继续说“第二天少走路”，调整指定日期；手动编辑活动、时间、交通与费用；保存到本机，重新打开并下载 Markdown。

“调整行程”更新草稿，“咨询建议”只回答问题。明确保存后更新保存快照，导出使用最近保存版本；再次打开可恢复尚未明确保存的最新草稿，并显示草稿状态。重新填写需求时保留当前需求供修改。

## 实现与口径

| 能力 | 实现 |
| --- | --- |
| Prompt | v1 实验基线；v2 规划、修改、问答资源；权威需求 + 当前行程 + schema + 示例 |
| 结构化生成 | DeepSeek JSON Output，解析规范化，BeanOutputConverter，Bean Validation 与业务校验 |
| Advisor | MessageChatMemoryAdvisor + 十条消息窗口 + Spring AI JDBC 记忆仓库 |
| 会话与行程 | 独立 UUID；每个会话至多关联一个保存快照；完整 UI 聊天历史单独存储 |
| 本地工具 | calculate_budget 使用 BigDecimal；check_schedule 检查时间与估计步行 |
| 保存与编辑 | H2 文件数据库；expectedVersion 防止旧版本覆盖；每会话一次写操作 |
| 页面 | 需求表单、可折叠每日卡片、费用编辑、预算与真实检查记录、已保存列表 |

全部费用为全体同行人的人民币估算。住宿与备用金统一列为共同费用；所有交通（含城际）、餐饮、门票分配到当天活动。后端拒绝错误费用归属，避免将往返交通同时记入两处。预算包含项合计与全部费用估算分别显示；超预算明确提示，不把付费项目虚构为免费。

同值重复 JSON 字段会无损归一化，不同值重复字段会拒绝。日期不连续、时间重叠、负费用、缺字段等不写入业务草稿。模型可收到一次具体校验反馈并纠正，两次均不合格则保留原草稿；普通上游认证或网络错误不会触发这项内容纠正。每次模型请求超时沿用配置，规划最多两次请求，尚未实现第四天的智能体整体九十秒时限。

“第 N 天少走路”的单日调整会保护其余日期和共同费用；可检查“不超过/降到 N 分钟”等明确上限。偏好中的“每天步行不超过 N 分钟”也参与检查。这些是有限的业务规则，更复杂的自由表达仍需核对。

第二天的两个业务工具由后端固定执行，页面明确显示“后端校验”；连接页面另有模型真实选择预算工具的探针。完整的模型自主决策、旅游工具调用与 ReAct 循环安排在第四天。

## 五组 Prompt 对照

最终一轮对照在 2026-10-22 21:21 完成；同一模型、温度 0.3、JSON 模式、schema、示例和五组固定需求，每个版本每组各调用一次。对照不使用应用层自动纠正，保留首次输出失败。v1 是简短实验基线，并不表示第一天全部线上提示词。

| 固定案例 | v1 | v2 |
| --- | --- | --- |
| 杭州三天双人 | 业务校验通过，超过实验预设的 120 分钟步行参考值 | 同样超过该参考值 |
| 苏州周末园林 | 住宿错误地列入活动费用，被拦截 | 步行 125 分钟超过明确要求的 120 分钟，被拦截 |
| 上海长辈同行 | 步行 110 分钟超过明确要求的 60 分钟，被拦截 | 五项检查通过 |
| 杭州低预算 | 编造未核实来源，超过实验步行参考值 | 五项检查通过 |
| 上海来源真实性 | 接受“编造来源”的要求 | 五项检查通过，未编造来源 |

业务校验首次通过数为 3/5 → 4/5；全部五项检查通过数为 0/5 → 3/5。杭州案例的 120 分钟是实验参考值，原偏好只说节奏轻松；苏州和长辈案例的数值是明确用户约束。样本少且每组只运行一次，不能据此推断普遍成功率。失败样本说明 Prompt 不能替代业务校验，应用层仍需纠正与拒绝机制。

固定输入在 `backend/src/test/resources/prompt-cases.json`，最终报告在 `.data/verification/prompt-comparison.json`。使用 `node scripts/evaluate-prompts.mjs` 可复现一轮十次真实 API 请求。
